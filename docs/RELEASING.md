# Releases and automatic updates

Publishing a GitHub release runs `.github/workflows/release.yml`. Use a SemVer tag such as `v0.1.0`, and ensure the tag contains the workflow, public updater key, and release scripts. The workflow builds macOS, Linux, and Windows for both `amd64` and `arm64`, tests each build, and attaches the resulting assets to that release.

## Signing setup

The updater uses the following signing secret:

| Value | Setup | Source |
| --- | --- | --- |
| `UPDATER_PRIVATE_KEY` | Required Actions repository secret | Complete PKCS#8 PEM private key generated by Wails; use the existing local key below. |
| `GITHUB_TOKEN` | Provided automatically by GitHub Actions | The workflow uses `github.token` with `contents: write` to upload release assets. |

The updater uses an Ed25519 key pair generated by `wails3 updater genkey`. Only the public key at `build/updater.key.pub` belongs in Git. The initial private key was generated locally at:

```text
/home/dev/.config/mier/release/updater.key
```

The repository's `UPDATER_PRIVATE_KEY` Actions secret was configured on **2026-10-14** using this file. Before uploading, the key was validated against both the local and remote master public keys; GitHub then confirmed the secret's name and update timestamp. Backing up the local private-key file in 1Password remains a maintainer step.

This private key already matches the committed public key. Back it up securely and set the repository's `UPDATER_PRIVATE_KEY` Actions secret to its complete PEM contents, including the `BEGIN PRIVATE KEY` and `END PRIVATE KEY` lines. Use the file directly; no extra base64 encoding is needed. With GitHub CLI installed, authenticate as an account allowed to manage this repository's secrets, then run these commands in the current workspace:

```sh
gh auth login --hostname github.com
gh secret set UPDATER_PRIVATE_KEY --repo Noah-Wilderom/mier \
  < /home/dev/.config/mier/release/updater.key
gh secret list --repo Noah-Wilderom/mier
```

Alternatively, open **Settings → Secrets and variables → Actions → New repository secret**, name it `UPDATER_PRIVATE_KEY`, and enter the complete private-key PEM. Use a repository secret; this workflow does not select a GitHub environment. The `secret list` command lists names and dates, not private-key contents.

The workflow fails before building if the secret is absent or does not match the committed public key. Never commit the private key or upload it as a release asset. Keep using the same signing key: installed apps trust the embedded public key, so replacing it requires a deliberate migration.

For a fresh project without an existing updater key, generate a pair outside the repository:

```sh
install -d -m 700 "$HOME/.config/mier/release"
wails3 updater genkey -out "$HOME/.config/mier/release/updater.key"
chmod 600 "$HOME/.config/mier/release/updater.key"
```

Wails writes the public key alongside it as `updater.key.pub`. Copy that public file to `build/updater.key.pub` and commit it before tagging a release; add the corresponding private file as `UPDATER_PRIVATE_KEY`. For this repository, use the already generated key instead. If it is lost, the public key cannot reconstruct it; restore a backup or plan a key migration before generating a replacement. The CLI refuses to overwrite an existing key unless explicitly forced. [Wails updater documentation](https://v3.wails.io/guides/updater/).

macOS release apps and DMGs are signed with Developer ID, notarized by Apple, and stapled before publication. The updater ZIP contains the signed and stapled app; both archives are unpacked and checked before upload. Development builds retain Wails' ad hoc signing. Windows installers have no Authenticode signature. Updater artifacts are separately signed with the local Ed25519 key; operating system signing is independent of update verification.

Apple certificate and account setup is maintained outside this repository. The release workflow requires that setup and stops if credentials, signing, or notarization fail. Windows certificate, Linux package-signing, and AUR credentials are not required. A personal access token is not required for uploading assets to this repository's release. [GitHub's automatic workflow token](https://docs.github.com/en/actions/concepts/security/github_token) and [repository secret setup](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets).

Apple notarization submits each artifact once, then waits on that submission ID in four 15-minute intervals. A wait timeout is followed by a status check; `In Progress` is pending, not a rejection. The ID and status are written to the job log and summary. Publication requires an explicit `Accepted` response, stapling, and verification. The macOS job allows three hours for the build and the separate app and DMG submissions; other platform jobs retain their 90-minute limit.

Use **Actions → Apple notarization status → Run workflow** to check up to ten existing submission IDs, separated by spaces or commas. This reads Apple's status without uploading a new artifact, importing a signing certificate, or publishing release assets. Apple may continue processing after the packaging job stops. Some submissions receive additional analysis and take longer; see [Apple's explanation](https://developer.apple.com/forums/thread/811968).

## Retrying a failed release

A missing signing secret causes **Validate release and signing key** to fail. GitHub then skips its dependent packaging and publication jobs. The packaging job uses GitHub's default matrix names, such as `package (linux, amd64, ubuntu-26.04)`, and displays `package` when skipped before expansion. The packaging step also explicitly names its platform and architecture. [GitHub job dependencies](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-jobs#defining-prerequisite-jobs).

After configuring the secret, open the failed run under **Actions** and choose **Re-run all jobs**. This reuses the existing release and tag; creating another release is unnecessary. From GitHub CLI, substitute the failed run's numeric ID:

```sh
gh run rerun RUN_ID --repo Noah-Wilderom/mier
```

Reruns use the original workflow and commit. Changes pushed to `master` do not change that run's scripts, actions, or runner labels. To use a code or workflow fix, publish a new release tag containing it; leave existing release tags in place. [GitHub rerun documentation](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs).

## Release assets

Each release contains:

- macOS: a ZIP containing one `MIER.app` bundle and a DMG for each architecture.
- Windows: a ZIP containing one executable and an NSIS setup EXE for each architecture.
- Linux: a `tar.gz` containing one executable, a DEB, RPM, Arch `.pkg.tar.zst`, and AppImage for each architecture.
- An AUR recipe archive containing `PKGBUILD` and `.SRCINFO`, with checksums pinned to both architecture downloads.
- `SHA256SUMS` for the downloads and `manifest.json` for the updater.

DMGs and setup installers are for first installation. Wails updates use the ZIP or `tar.gz` archives, because its updater does not install DMGs or NSIS packages. Windows setup installs for the current user, allowing the updater to replace the executable without elevation. Linux needs the GTK 4 and WebKitGTK 6 runtime libraries; its archive does not bundle them. All six targets now use a matching native runner architecture. Linux releases build in a pinned Ubuntu 24.04 container on Ubuntu 26.04 hosts to retain the glibc 2.39 compatibility baseline; the native test matrix also tests Ubuntu 26.04 directly.

All six archives must exist before the workflow signs the feed. It verifies every archive with the pinned public key, uploads the downloads, then uploads the manifest last. Release version metadata is written into the executable, macOS bundle, and Windows installer.

## Command-line installation

The root `install.sh` requires Bash, `curl`, `jq`, and either `sha256sum` or `shasum`. It detects Linux/macOS/Windows and AMD64/ARM64, including Rosetta and an AMD64 shell on ARM64 Windows. On Windows, use Git Bash, MSYS2, or Cygwin.

```sh
bash install.sh               # latest stable
bash install.sh --alpha       # latest alpha only
bash install.sh --beta        # latest beta only
bash install.sh --rc          # latest release candidate only
bash install.sh --alpha --dry-run
```

Selection compares SemVer across paginated published releases, excludes drafts, and never substitutes another channel. An unavailable channel reports an error; the initial `v0.1.0-alpha.1` release therefore needs `--alpha`. Downloads must have their matching asset, `SHA256SUMS`, and the final `manifest.json` publication marker. The script verifies the selected download before changing an installation.

Linux selects pacman, dnf, or apt when available and lets that manager install the native package and dependencies. `--portable` instead installs a user-owned AppImage and a FUSE-free launcher, with a `~/.local/bin/mier` alias. A custom `--prefix DIR` also selects portable Linux installation and places the launcher at `DIR/mier`. macOS installs the ZIP's complete `MIER.app` bundle into `~/Applications`, or the directory given by `--prefix`; a failed replacement restores the previous bundle. Windows runs the architecture-matched setup EXE silently for the current user; `--prefix` is unavailable there. Close M.I.E.R. before upgrading. Installer signing remains as described above; checksums establish download integrity and do not provide macOS notarization or Windows Authenticode.

## App behavior

**About M.I.E.R.** shows the installed GitHub release version, including any alpha, beta, or rc suffix. The version is embedded from the release tag when the app is built; development builds show `dev`.

Portable release builds check the latest stable release quietly on startup and use Wails' periodic checks every six hours. **M.I.E.R. → Check for Updates…** on macOS, or **Help → Check for Updates…** on Windows and Linux, checks manually. Wails displays the download and restart flow when an update is found. Development builds disable updates. Linux packages installed under `/usr` or `/opt` use their package manager for upgrades; AppImages are replaced as whole files. Those installations disable the binary-replacement updater. See [Linux installation](LINUX.md) for CLI commands.

The endpoint is `https://github.com/Noah-Wilderom/mier/releases/latest/download/manifest.json`. The app rejects unsigned feeds and incorrect signatures before downloading, then Wails verifies the downloaded bytes before staging and replacing the installed application. Prereleases can have downloadable assets, but GitHub's latest stable release endpoint does not offer them to this channel.

## Local checks

Build frontend assets before Go tests: the Go executable embeds `frontend/dist`, so do not rebuild it concurrently with Go tests.

```sh
npm --prefix frontend ci
npm --prefix frontend test
npx --prefix frontend playwright install --with-deps chromium webkit
npm --prefix frontend run test:ui
node --test scripts/release.test.mjs
node --test scripts/install.test.mjs
shellcheck install.sh
actionlint .github/workflows/test.yml .github/workflows/release.yml
npm --prefix frontend run build
go test ./...
go vet ./...
wails3 build
```

The test workflow runs native checks on Linux, macOS, and Windows, with Go race detection on Linux and macOS. A separate Linux job runs the retained Chromium/WebKit UI suite and retains failure traces. The release workflow also requires that UI suite on its Linux AMD64 job before publication. Dedicated AMD64/ARM64 Linux package jobs use the same Ubuntu 24.04 compatibility container as releases, while native tests/builds run directly on Ubuntu 26.04. Those package jobs build all four installer formats and extract them to verify architecture, dependencies, desktop files, permissions, and bundled AppImage subprocesses. The release helper passes `GOARCH` to Wails' build/package commands and validates the executable's actual CPU architecture before archiving it. `ARCH` is a Task variable; the Wails command wrappers replace it with their resolved `GOARCH`.

The release workflow generates the AUR recipe after both Linux builds finish and includes it in the release checksums. Publishing that recipe to the AUR is a separate maintainer action; this workflow does not modify the AUR or Omarchy's package repository. M.I.E.R. remains unlicensed by maintainer choice. There is no project `LICENSE`, and Linux package metadata reports `unknown`.

All external actions are pinned to verified release commits: [checkout 7.0.1](https://github.com/actions/checkout/releases/tag/v7.0.1), [setup-node 7.1.0](https://github.com/actions/setup-node/releases/tag/v7.1.0), [setup-go 7.0.0](https://github.com/actions/setup-go/releases/tag/v7.0.0), [upload-artifact 7.0.2](https://github.com/actions/upload-artifact/releases/tag/v7.0.2), and [download-artifact 8.0.2](https://github.com/actions/download-artifact/releases/tag/v8.0.2), checked on 2026-10-14. They declare Node 24 as their action runtime, removing the former artifact-action Node 20 warning. This runtime is independent of the Node version installed for frontend commands.

Hosted labels follow GitHub's current [runner image catalog](https://github.com/actions/runner-images): Ubuntu 26.04 for both architectures, macOS 26 for Intel and ARM64, Windows Server 2025 with Visual Studio 2026 for AMD64, and Windows 11 with Visual Studio 2026 for ARM64. The three newest labels are registered in `.github/actionlint.yaml` because actionlint 1.7.12's bundled catalog predates them. Weekly grouped Dependabot updates maintain the action pins; runner major versions and the Linux compatibility container remain deliberate upgrades.
