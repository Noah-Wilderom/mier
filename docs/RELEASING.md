# Releases and automatic updates

Publishing a GitHub release runs `.github/workflows/release.yml`. Use a SemVer tag such as `v0.1.0`, and ensure the tag contains the workflow, public updater key, and release scripts. The workflow builds macOS, Linux, and Windows for both `amd64` and `arm64`, tests each build, and attaches the resulting assets to that release.

## Signing setup

The updater uses an Ed25519 key pair generated by `wails3 updater genkey`. Only the public key at `build/updater.key.pub` belongs in Git. The initial private key was generated locally at:

```text
/home/dev/.config/mier/release/updater.key
```

Back up this private key securely and set the repository's `UPDATER_PRIVATE_KEY` Actions secret to its PEM contents. With GitHub CLI authenticated for repository administration:

```sh
gh secret set UPDATER_PRIVATE_KEY --repo Noah-Wilderom/mier \
  < /home/dev/.config/mier/release/updater.key
```

The workflow fails before building if the secret is absent or does not match the committed public key. Never commit the private key or upload it as a release asset. Keep using the same signing key: installed apps trust the embedded public key, so replacing it requires a deliberate migration.

Platform installers initially have no Developer ID signature, notarization, or Windows Authenticode signature. macOS bundles use Wails' ad hoc signing. Updater artifacts are separately signed with the local Ed25519 key; operating system installer signing is independent of update verification.

## Release assets

Each release contains:

- macOS: a ZIP containing one `MIER.app` bundle and a DMG for each architecture.
- Windows: a ZIP containing one executable and an NSIS setup EXE for each architecture.
- Linux: a `tar.gz` containing one executable, a DEB, RPM, Arch `.pkg.tar.zst`, and AppImage for each architecture.
- An AUR recipe archive containing `PKGBUILD` and `.SRCINFO`, with checksums pinned to both architecture downloads.
- `SHA256SUMS` for the downloads and `manifest.json` for the updater.

DMGs and setup installers are for first installation. Wails updates use the ZIP or `tar.gz` archives, because its updater does not install DMGs or NSIS packages. Windows setup installs for the current user, allowing the updater to replace the executable without elevation. Linux needs the GTK 4 and WebKitGTK 6 runtime libraries; its archive does not bundle them. macOS and Linux use native runners. Windows ARM64 is cross-built on a Windows AMD64 runner.

All six archives must exist before the workflow signs the feed. It verifies every archive with the pinned public key, uploads the downloads, then uploads the manifest last. Release version metadata is written into the executable, macOS bundle, and Windows installer.

## App behavior

Portable release builds check the latest stable release quietly on startup and use Wails' periodic checks every six hours. **Help → Check for Updates…** checks manually. Wails displays the download and restart flow when an update is found. Development builds disable updates. Linux packages installed under `/usr` or `/opt` use their package manager for upgrades; AppImages are replaced as whole files. Those installations disable the binary-replacement updater. See [Linux installation](LINUX.md) for CLI commands.

The endpoint is `https://github.com/Noah-Wilderom/mier/releases/latest/download/manifest.json`. The app rejects unsigned feeds and incorrect signatures before downloading, then Wails verifies the downloaded bytes before staging and replacing the installed application. Prereleases can have downloadable assets, but GitHub's latest stable release endpoint does not offer them to this channel.

## Local checks

Build frontend assets before Go tests: the Go executable embeds `frontend/dist`, so do not rebuild it concurrently with Go tests.

```sh
npm --prefix frontend ci
npm --prefix frontend test
node --test scripts/release.test.mjs
npm --prefix frontend run build
go test ./...
go vet ./...
wails3 build
```

The test workflow runs these checks on Linux, macOS, and Windows, with Go race detection on Linux and macOS. Linux CI also builds all four installer formats and extracts them to verify architecture, dependencies, desktop files, permissions, and bundled AppImage subprocesses. The release helper passes `GOARCH` to Wails' build/package commands and validates the executable's actual CPU architecture before archiving it. `ARCH` is a Task variable; the Wails command wrappers replace it with their resolved `GOARCH`.

The release workflow generates the AUR recipe after both Linux builds finish and includes it in the release checksums. Publishing that recipe to the AUR is a separate maintainer action; this workflow does not modify the AUR or Omarchy's package repository. The repository currently has no project `LICENSE`, so package metadata reports `unknown` instead of inheriting the template's MIT declaration. Choose the project license before publishing to the AUR.
